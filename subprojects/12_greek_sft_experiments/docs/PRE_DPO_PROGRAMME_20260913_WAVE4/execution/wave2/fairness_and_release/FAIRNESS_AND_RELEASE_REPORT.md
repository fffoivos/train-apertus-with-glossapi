# Krikri fairness and release-transparency gate

Checked 13 September 2026 against current official Hugging Face metadata, the ILSP model cards, the final EMNLP paper, and local benchmark artifacts. No evaluation was launched.

## Fair comparison decision

The strongest fair Krikri comparison is a **two-checkpoint envelope**, with every score still reported by named checkpoint. The original [`ilsp/Llama-Krikri-8B-Instruct`](https://huggingface.co/ilsp/Llama-Krikri-8B-Instruct) is the instruction-following reference at revision `06d813157ba5f19deb17d70c3862ce64035431ec`. The chat-focused [`ilsp/Llama-Krikri-8B-Instruct-v1.5`](https://huggingface.co/ilsp/Llama-Krikri-8B-Instruct-v1.5) is the open-ended chat reference at revision `326e2c0ea90d771c19fcf06225fe87dc922b51b2`. Both descend from `ilsp/Llama-Krikri-8B-Base`, currently pinned at `0383614fccad6679644b03319b3841d927a0db3f`.

This is required by ILSP's own matched table: original versus v1.5 is **67.5% versus 61.2%** on Greek IFEval and **82.4% versus 78.8%** on English IFEval, while v1.5 leads **8.16 versus 7.96** on Greek MT-Bench and **7.38 versus 7.21** on English MT-Bench. The v1.5 card explicitly calls the original stronger at instruction following and v1.5 stronger on Greek chat benchmarks. The final [EMNLP paper](https://aclanthology.org/2025.findings-emnlp.268/) documents the original multi-stage post-training model; the v1.5 card adds a second pseudo-on-policy DPO stage but says further methodology is forthcoming.

Do not create a per-item oracle that picks whichever Krikri answer is better, and do not call the maximum of two checkpoint scores one model result. For promotion claims, compare instruction/constraint endpoints to original Krikri and broad chat endpoints to v1.5. Show both versions on every newly run shared endpoint so the tradeoff is visible.

At the pinned revisions, the two chat templates are byte-identical after extraction, SHA-256 `e10ca381b1ccc5cf9db52e371f3b6651576caee0a630b452e2816b2d404d4b65`. Their repository generation defaults are also the same (`do_sample=true`, temperature `0.6`, top-p `0.9`), but those defaults are unsuitable for a controlled comparison. The local fixed benchmarks explicitly use temperature `0`, top-p `1`, no system prompt, the pinned native chat template, 2,048 output tokens for MATH-500 and 1,024 elsewhere. Use the same prompts, decoding, stop handling, output cap, scorer, language normalization and item exclusions for all models. Log-likelihood suites must use the same FP32 candidate construction, token normalization, batching and aggregation. Published card scores provide context; they are not substitutes for locally matched measurements.

## What is already measured and what remains

The original checkpoint already has complete local results for ILSP Greek IFEval (541), MGSM (250), GreekMMLU (16,632 full; 16,159 clean), Greek and English MATH-500 (500 each), Greek and English IFBench (300 each), generated Greek and English XSTest (450 each), generated Greek and English MultiChallenge (262 usable each), Greek judging for the latter two, and 60 mixed-profile dialogues containing 808 target turns. English XSTest/MultiChallenge judgement is absent. The v1.5 checkpoint has no local result artifact.

Neither checkpoint has the local cached retention suite or the eight non-GreekMMLU native Greek task families. Those native families total 73,894 scored examples per model under the existing sharded runner, so they should not be smuggled into a “small” first evaluation. Matched local MT-Bench and Arena-Hard are also absent for both versions. The exact cell ledger is in `remaining_peer_matrix.jsonl`.

The first CSCS proposal therefore fills v1.5's deterministic cells only: 3,024 fixed benchmark generations plus 791 ILSP examples after an eight-item-per-cell smoke test. It deliberately defers judge calls, interactive simulation, the 16,632-item GreekMMLU run, the 73,894-example native suite and retention. This is one proposed debug allocation, one node/four GPUs, capped at 90 minutes; it is not authorized or launched. Existing original-Krikri results may be reused only if their frozen data and generation hashes match the new receipt.

## Required release bundle

Before a dataset or model-card release, produce these concrete deliverables:

1. A row-level provenance ledger with release row ID, block, upstream repository/config/split/source row ID, immutable revision, original license and URL, generator model/revision, transformation type, local content hash and redistribution mode: `exact_rows`, `reconstruct`, `metadata_only` or `hold`.
2. Revision-pinned intake and reconstruction scripts. They must fail on revision drift, preserve native tool schemas/call/result IDs, and emit input/output counts plus hashes. Never use an unqualified `main` in a release recipe.
3. Every authoring, translation, correction, judging and filtering prompt with model name/revision, reasoning effort, temperature/top-p, batch size, retry policy, schema and code revision. Historical rows lacking these fields must be labelled incomplete rather than reconstructed from memory.
4. An append-only repair ledger: row ID, before/after hashes and spans, reason, reviewer class, semantic versus language scope, guard results, quarantine/reinstatement and superseded version. Publish v1 and later repairs as distinct identities.
5. A decontamination manifest covering every training version against every released evaluation set in both Greek and source languages. Include exact and normalized hashes, n-gram/template rules, exclusions, false-positive review, counts and the known CPT-visibility gap. Benchmark items and their translations stay outside training.
6. A complete mixture receipt with unique rows, weighted exposures, train/dev split, rendered and supervised tokens, per-block token weights, duplicate handling, truncation, masks, selection rates and final model/tokenizer/template hashes. Publish the actual realized mix, beyond target percentages.
7. Greek quality evidence: deterministic stratified full-row samples by block/task/length/risk, separate targeted-defect samples, native-review instructions, denominators, dispositions and residual-rate intervals after repair. Personality v4 requires all 192 rows read, with a second reviewer on all 48 capability rows. Tool use requires an all-row structural audit before semantic sampling.
8. A permissions and attribution file distinguishing code, database structure, individual text, translations, synthetic outputs and model weights. Include the Llama 3.1 model license separately from dataset permissions and document any access-controlled reconstruction dependencies.
9. A benchmark reproducibility bundle with item IDs but no training copies, dataset/code revisions, exact prompt rendering hashes, decoding, judge/baseline versions, order randomization, scorer code, raw-output hashes, per-item results and exclusions.

These requirements would make the release auditable. They do not yet justify saying our data process is more transparent than Krikri's: ILSP already publishes model cards, mixture-scale counts, methods, checkpoint weights and public benchmarks, while our upstream revision pins and transitive license ledger are currently incomplete. Any future comparison should name the exact artifacts that are more reproducible rather than claim general transparency superiority.
