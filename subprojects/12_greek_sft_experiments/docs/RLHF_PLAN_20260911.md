## 1. What RL is for here, measured

Arm B's failures that SFT data alone may not remove (R0 hostile / R1 benign, docs/ROBUSTNESS_PROGRAM §8 to §9):

| behaviour | arm B | note |
|---|---:|---|
| tail copied from the previous answer | 14.4% / 5.8% | self-reinforcing repetition (DITTO literature) |
| dead dialogues (three broken turns in a row) | 20.0% / 8.3% | |
| stale after a redirect or correction | 77.5% | the largest number on the sheet |
| requests honoured (judge) | 47.5% | |
| standing instruction kept on later turns | 67.6% | regex-checkable |
| self-observation and recap answered correctly | 21 to 26% | |
| redirect or redo addressed | 34.7% | |

R3 trains on the suite and the correcting set, so these numbers will move before RL starts; RL is for what remains, plus qualities no checker sees: Greek naturalness, answer length calibrated to the request, personality consistency, and honest correction handling. Two literature cautions we adopted in MULTITURN_FIXES §1: preference optimisation moved multi-turn scores little in MT-Bench-101, and preference models can prefer sycophantic answers (Sharma et al. 2023, arXiv:2310.13548; the exact rate and its experimental scope are being verified, see §8). The rating design below is built around not rewarding sycophancy and length.

## 2. Reward sources, in order of trust (owner rule: verified beats judged)

1. **Programmatic verifiers we already own, zero rater cost, no judge bias.** Greek IF checkers (40 constraint families, data/greek_if/constraints.py); math answer match (greek_math, openmath); the suite's regex checks (S1 list retention, standing-instruction regexes on every later turn, loop and tail-copy detectors, language-slip detector, banned phrases, the question counter); the correcting set's typed checks (user_questions, false_concession, invented_process, unverified_url, wrong_count, forbidden self-claims); the identity fact-sheet regexes. These give exact rewards for instruction following, math, retention, repetition and the correction contract.
2. **Sol as judge** for what the verifiers cannot see: helpfulness on open requests, faithfulness to the conversation, Greek quality, length fit, tone, and correction handling beyond the typed checks. Protocol in §4.
3. **A trained Greek reward model: not now.** It needs 20k+ clean pairs and its own evaluation; it becomes worth it only if judge calls dominate cost after two iterations.

## 3. Algorithm: iterative on-policy DPO first, GRPO on verifiable rewards second

**Recommendation for iteration 1: DPO on on-policy pairs, from the R3 checkpoint.**

- Sampling: k = 4 responses per prompt at temperature 0.8 from OUR model on the cluster (vLLM serving as in R0/R1). The laptop is for pilots only (about 25 tokens/s; 800 generations take an afternoon).
- Pair construction: chosen = the best response that passes every hard veto (§4.3), rejected = the worst; drop the prompt when all k pass or all k fail (no signal), when the judge's two orders disagree, and when chosen is more than 1.5× the length of rejected unless the task asks for length. Verifier prompts need no judge.
- Training: TRL DPOTrainer, β = 0.1, learning rate 5e-7, one epoch, reference = the R3 checkpoint frozen, with an SFT anchor term (RPO α = 1) so Greek likelihood does not collapse. Keep fp32 master weights with bf16 autocast exactly as cluster/sft_train.py does (it asserts fp32 parameters): our rl-study measurement (2026-08-20, a different model and recipe) showed bf16 parameters at lr 5e-6 left 97.65% of weights bitwise unchanged, which is the reason to keep fp32 accumulation at 5e-7; it does not by itself prove what a bf16 run would do here.
- Iterate: sample again from the updated policy, rate, train (two iterations planned), because off-policy pairs (a Sol rewrite as chosen) are weaker than on-policy ones (Tajwar et al. 2024) and the CHAT_REVIEW idea of rewrite-as-chosen is kept only for the loop failures where the model never produces a good sample.
- Seeds: two seeds on the DPO stage (about 1 nh each) so a difference below seed noise is not promoted.

**Iteration 2 candidate: GRPO with verifiable rewards** (TRL GRPOTrainer with a colocated vLLM generator) on Greek IF levels 4 to 5, math and the retention regexes, where the reward is exact. Larger infrastructure lift on Clariden (generator and trainer share the node's four GPUs); worth it if DPO iteration 1 leaves IF or retention short.

## 4. How we actually rate (to decide together)

**4.1 Unit of rating.** One assistant turn given a fixed prefix. Prefixes are on-policy dialogues: the model's own earlier turns and a user turn that reacts to them (the responder rule in data/robustness/simulate.py), from the R0/R1 transcripts, replays of the owner's chats, and the correcting-set and suite contexts. Never rate a whole dialogue at once: credit assignment over several turns is what made the R0 judge unreliable (ROBUSTNESS §10 F3).

**4.2 Comparison format: k-way ranking in one call, two shuffled orders.** For each prompt the judge sees the prefix and the k = 4 candidates in random order and returns per-candidate rubric fields plus a full ranking; a second call with a different order. Pairs are taken only where both orders agree on the relative order of the two responses. Cost: 2 calls per prompt instead of 2 × C(4,2) = 12 pairwise calls. Alternatives to discuss: pure pairwise (most reliable per pair, 6× the cost), pointwise absolute scores (cheapest, worst calibration).

**4.3 The rubric the judge returns (JSON schema, like every generator we run):**

| field | values | use |
|---|---|---|
| task_done | 0 / 1 / 2 | ranking |
| faithful_to_prefix | 0 / 1 / 2 with the quoted evidence | ranking; 0 is a veto |
| invented_fact | true / false with the span | veto |
| conceded_false_claim | true / false | veto (sycophancy); the judge is given claim_truth for correction prompts, as the responder is |
| self_claim | true / false with the span (capabilities, history, tools it does not have) | veto |
| greek_errors | list of spans with the corrected form | veto above 2; the guarded-polish rule |
| length_fit | under / ok / over, given the request | tie-break, and the 1.5× rule |
| tone | fine / curt / snarky / servile | servile is a veto on correction prompts |
| ranking | permutation of the k candidates | the pair |

Vetoes are hard: a vetoed response can be rejected but never chosen. This is how the flags carry the owner's rules (no invented facts, no self-claims, no false concessions) into the reward without trusting the judge's overall taste.

**4.4 Biases we control, with our own evidence.**
- Position: two orders, agreement required (S3c precedent).
- Length: the judge is told the request's length expectation; the 1.5× rule; the R1 measurement that repetition penalty 1.1 doubled answer length is the reminder that length moves easily.
- Self-preference: Sol rating text in Sol's own style (our SFT data is Sol-written). Mitigation: a second judge (Opus, or Luna) on a fixed 10% audit subset every iteration, with agreement reported; disagreement above 20% on non-ties stops the iteration (astra R9: one calibrated primary judge plus a second judge on a predefined audit subset).
- Greek competence: Sol's editor pass had 34 of 235 edits reverted by guards; greek_errors verdicts are spot-checked by the owner on the calibration set before they veto anything.
- Sycophancy: claim_truth in the judge's view; conceded_false_claim veto; the sycophancy flip rate is a promotion floor, not just a training signal.
- Prompt language: instructions in English, content in Greek (our standing rule for Sol).

**4.5 Calibration before any training: the owner's blind set.** 150 prompts × 2 candidates, rated blind by the owner on a page like the pilot pages, in both orders for 30 of them. Targets: Sol–owner agreement ≥ 80% on non-ties, Sol position consistency ≥ 90%, greek_errors precision ≥ 80% on the owner's check. Below target, the rubric is revised and the pilot repeated; no pair enters training from an uncalibrated judge (the 2026-09-05 Luna lesson: judge labels never become filters silently).

**4.6 Data for iteration 1 (proposed sizes).**

| family | prompts | reward | judge calls |
|---|---:|---|---:|
| Greek IF, levels 3 to 5, new prompts from the generator (unseen) | 3,000 | checkers | 0 |
| Greek math, native cut 2 (unseen) | 2,000 | answer match | 0 |
| retention and standing-instruction contexts (suite lanes, unseen items) | 1,500 | regexes | 0 |
| correction contexts (misquote, false correction, planted failures) | 1,500 | typed checks + judge | 3,000 |
| open chat and owner-chat replays, personality-style prompts (not the dev holdout) | 2,500 | judge | 5,000 |
| **total** | **10,500 prompts, k = 4 → 42,000 generations** | | **8,000 calls** |

Generation: 42,000 × ~300 tokens ≈ 13M tokens on vLLM, about 1.5 to 2 nh per iteration. Judging: 8,000 calls ≈ **32% of a Sol week per iteration** at the measured 0.004% per high-effort call (corrected 2026-09-11 18:00: the first draft said 3.2%, a tenfold error caught by the astra review), two days at 24 workers on hotel Wi-Fi with the app-server client. Two iterations would take 64% of a week, so the judged families must shrink or be batched: several candidates per call (the k-way format already does this), medium effort, fewer judged prompts (1,500 correction + 1,500 open chat = 3,000 prompts → 6,000 calls ≈ 24%), or one iteration per weekly bucket. Expected pairs after the drop rules: 5,000 to 7,000 at the original sizes, 3,500 to 5,000 at the reduced ones.

**4.7 Generation settings for the pairs (answer to the owner, 2026-09-11 19:00; aligned with DOC C §5).**

Sampling policy: the R3 checkpoint served by vLLM (eval copy, Apertus chat template, no system prompt), on ONE node: four replicas, one per GPU (serve_models.sh), client load-balanced over the four ports. Sampling is embarrassingly parallel, so more nodes only shorten a window that is already about an hour: 24,000 responses × ~300 tokens ≈ 7M tokens, and vLLM on a GH200 delivers thousands of tokens per second per GPU at batch 64; the first window measures the real rate and it is recorded here. Settings: temperature 0.8, top_p 0.95, no repetition penalty (1.1 doubled answer length in R1; 1.05 stays a serving-time option, not a training-data one), max_tokens 1,024 for chat and IF, 2,048 for math, k = 4 samples per prompt with distinct seeds, plus one capped resampling round at temperature 1.0 for prompts where all four fail a verifier (DOC C: recovery, tracked separately). Every candidate, its settings, seed and the serving commit are stored (DOC C: storage).

Prompt sources, first iteration (about 6,000 prompts, DOC C's allocation, adapted to the pools we own):

| family | prompts | source | reward |
|---|---:|---|---|
| redirects and correction handling | 1,500 | prefixes from the R0/R1 arm-B transcripts (60 + 180 dialogues, cut at each redirect or correction turn), the correcting set's held-out dialogue shells, and 34 owner chats; last turn sampled from R3 | typed truth checks (claim_truth known) + judge |
| standing instructions and retention | 900 | suite generator with unseen items (S1/S2/S3c contexts), instruction regexes on the last turn | regexes + semantic audit sample |
| recap and self-observation | 600 | prefixes from the same transcripts at recap points; the answer must be grounded in the prefix | typed checks where possible + judge |
| Greek verifiable IF | 900 | the 2,751 prompts Sol failed twice during the SFT build (data/greek_if/v{1,2,3}/out/rejected_only.jsonl: unseen in training, authored, hard) sampled by level 3 to 5 | checkers |
| Greek math | 600 | SFT-seen native and translated problems where R3's greedy answer is wrong (identified in the battery) plus the reference-verified pool; unseen Greek math needs a Sol translation batch, deferred | answer match |
| naturalistic Greek open chat, owner-style requests | 1,000 | owner chats (turn 1), personality-style prompts outside the dev holdout, greek_ours-style requests rephrased | judge |
| English and EU-language preservation | 500 | smoltalk2 and Nemotron dev prompts | language check + judge |

Two rules from DOC C adopted here: prompts that come from R0/R1 or owner chats become development evidence once they inform training, so the promotion battery uses separate final conversations; and there is no universal 1.5× length filter, length is a judge field instead.

## 6. Promotion floors for an RL checkpoint (pre-registered, same battery as R3)

No drop beyond seed noise on Greek IFEval strict, Greek MGSM, GreekMMLU, retention (English suite), native Greek suite; identity probe 40/40; language slips ≤ arm B; sycophancy flip rate ≤ R3; tail-copy and dead-dialogue rates ≤ R3; mean answer length within ±25% of R3 unless the judged length_fit improves. Primary metric: the picky-user coherent-turns and requests-honoured rates, paired by dialogue, with the owner's blind adjudication of a stratified sample (DATA_TODO 34).

## 7. Decisions for the owner

1. k-way ranking with two orders (recommended) vs pairwise vs pointwise.
2. Whether you rate the 150-prompt calibration set yourself (about an hour) before iteration 1.
3. DPO first (recommended) vs GRPO-on-verifiers first.
4. Rewrite-as-chosen pairs: only for loop failures (recommended) or never.
5. Length policy: the 1.5× drop rule (recommended) vs no rule.
6. Second judge on the audit subset: Opus (recommended: a different vendor) vs Luna.
7. Budget: about 21 nh ≈ CHF 57 for two iterations (or about 11 nh for one), and Sol calls at 0.004% of the weekly bucket each: 8,000 calls (32% of a week) per iteration at the draft sizes, 6,000 (24%) at the reduced sizes; on top of the 19 to 21 nh for R3 and its benchmarks.
